# PayFlow

Веб-приложение для учёта клиентов, выставления счетов и отслеживания платежей организаций. Проект включает основной API и отдельный сервис Mock PSP, который имитирует платёжного провайдера.

PayFlow разрабатывается как учебный и дипломный проект. Реальные деньги не списываются.

## Возможности

- Регистрация и авторизация пользователей через JWT.
- Создание организаций и управление участниками.
- Роли `owner`, `manager` и `viewer` с проверкой доступа к данным организации.
- Создание, просмотр, редактирование и удаление клиентов.
- Кеширование списка клиентов в Redis и сброс кеша после изменений.
- Создание счетов, редактирование черновиков, выставление и отмена.
- Создание платежей по выставленным счетам.
- Запрет нескольких незавершённых платежей для одного счёта.
- Отправка платежа в Mock PSP и сохранение идентификатора транзакции провайдера.
- Повторная отправка платежа после ошибки связи с PSP.
- Идемпотентное создание транзакций в Mock PSP: повтор с теми же параметрами возвращает существующую операцию.
- Имитация успешного и неуспешного завершения транзакции в Mock PSP.
- Интерфейс для работы с организациями, участниками, клиентами, счетами и платежами.

**Текущее ограничение:** автоматическая доставка результата из Mock PSP в PayFlow через webhook ещё разрабатывается. Завершение транзакции в PSP пока само по себе не обновляет статус платежа и счёта в PayFlow.

## Архитектура

Основное приложение организовано по слоям:

- `api` — HTTP-маршруты, зависимости и преобразование ошибок в HTTP-ответы;
- `schemas` — валидация запросов и схемы ответов;
- `services` — бизнес-правила, проверки доступа и границы транзакций;
- `repositories` — запросы к базе данных;
- `models` — ORM-модели;
- `integrations` — взаимодействие с внешними сервисами.

Mock PSP работает как отдельное FastAPI-приложение со своей базой данных и миграциями. Обращения к его API защищены заголовком `X-API-Key`.

Сетевой запрос к PSP выполняется вне транзакции основной БД. Если провайдер не ответил, локальный платёж сохраняется в `pending`; его можно отправить повторно с тем же идентификатором.

## Основные сущности

| Сущность | Назначение |
| --- | --- |
| User | Пользователь приложения |
| Organization | Организация, которой принадлежат данные |
| Membership | Участие пользователя в организации и его роль |
| Customer | Клиент организации; регистрация в приложении не требуется |
| Invoice | Счёт клиенту с суммой, валютой и статусом |
| Payment | Попытка оплаты счёта и связь с провайдером |
| Transaction | Операция в отдельной базе Mock PSP |

Денежные суммы хранятся целыми числами в минимальных единицах валюты: `10000` означает `100.00 RUB`. Поддерживаемая валюта — RUB.

Статусы счетов: `draft`, `issued`, `paid`, `cancelled`.

Статусы платежей и транзакций PSP: `pending`, `succeeded`, `failed`.

## Права доступа

| Действие | owner | manager | viewer |
| --- | --- | --- | --- |
| Просмотр данных организации | Да | Да | Да |
| Управление участниками | Да | Нет | Нет |
| Изменение клиентов и счетов | Да | Да | Нет |
| Создание и повторная отправка платежей | Да | Да | Нет |

Проверки доступа выполняются на backend. Роль владельца нельзя изменить через управление участниками, а самого владельца нельзя удалить из организации.

## Запуск

Понадобятся Git, Docker с Docker Compose и Node.js с npm для фронтенда. Backend запускается в контейнерах; локальное Python-окружение для этого не требуется.

### 1. Подготовить окружение

Откройте терминал в корне клонированного репозитория. Создайте `.env` из `.env.example`.

**PowerShell:**

```powershell
Copy-Item .env.example .env
```

**macOS / Linux:**

```bash
cp .env.example .env
```

Если `.env` уже существует, сохраните его настройки вместо перезаписи.

Заполните переменные:

| Переменная | Назначение |
| --- | --- |
| `POSTGRES_DB` | Имя основной базы |
| `POSTGRES_USER` | Пользователь основной базы |
| `POSTGRES_PASSWORD` | Пароль основной базы |
| `PSP_POSTGRES_PASSWORD` | Пароль базы Mock PSP |
| `JWT_SECRET_KEY` | Секрет для подписи JWT |
| `PSP_API_KEY` | Общий ключ PayFlow и Mock PSP, минимум 32 символа |

Дополнительные настройки приложения: `JWT_ALGORITHM`, `ACCESS_TOKEN_EXPIRE_MINUTES`, `CACHE_TTL_SECONDS`, `PSP_TIMEOUT_SECONDS`.

Compose задаёт адреса подключений внутри контейнеров через `DATABASE_URL`, `PSP_DATABASE_URL`, `REDIS_URL` и `PSP_BASE_URL`. Для локального запуска через Uvicorn эти значения нужно задать в `.env` с адресами компьютера.

`.env` содержит секреты и не должен попадать в Git. В `.env.example` размещаются только примеры. Пароли со специальными символами требуют корректного URL-кодирования при включении в строки подключения к БД.

### 2. Запустить backend

Запустите Docker Desktop, затем выполните:

```bash
docker compose config --quiet
docker compose up --build
```

Команда собирает образы и запускает сервисы с логами в терминале. Перед стартом API автоматически применяются миграции соответствующей базы. Если миграции завершаются с ошибкой, приложение не запускается.

Для фонового запуска:

```bash
docker compose up -d --build
docker compose logs -f app psp
```

Остановите ранее запущенные локальные Uvicorn на портах 8000 и 8001, чтобы избежать конфликта портов.

### 3. Запустить frontend

В отдельном терминале:

```bash
cd payflow-frontend
npm install
npm run dev
```

Фронтенд пока запускается отдельно от Docker. Запросы `/api` направляются через Vite-прокси к PayFlow на порту 8000.

| Сервис | Адрес на компьютере |

## Проверка интеграции

1. Зарегистрируйтесь и войдите в PayFlow.
2. Создайте организацию и клиента.
3. Создайте счёт и переведите его из `draft` в `issued`.
4. Создайте платёж по этому счёту.
5. Проверьте, что у платежа появился `provider_transaction_id`.
6. Откройте Swagger Mock PSP и нажмите **Authorize**.
7. Введите значение `PSP_API_KEY` без префикса `Bearer`.
8. Получите транзакцию через `GET /transactions/{transaction_id}`, используя `provider_transaction_id`.
9. Для имитации результата вызовите `POST /transactions/{transaction_id}/complete`:

```json
{
  "status": "succeeded"
}
```

Для неуспешного результата используйте `failed`. Повторное завершение с тем же статусом возвращает существующий результат; изменение завершённой операции на противоположный результат запрещено.

Пока webhook не подключён, шаг 9 меняет статус только в Mock PSP.

## Тесты

Тесты используют отдельные базы PostgreSQL. Запускайте их из локального Python-окружения, если настройки тестовых фикстур указывают на `127.0.0.1:5434` и `127.0.0.1:5436`. Эти адреса не подходят для запуска тестов внутри контейнера приложения.

Запуск тестовых баз:

```bash
docker compose up -d db_test psp_db_test
```

Установите зависимости в локальное виртуальное окружение:

```bash
python -m pip install -r requirements.txt
```

Перед первым запуском тестов и после изменений схемы примените миграции к тестовым базам.

**PowerShell — в отдельном терминале с активированным окружением:**

```powershell
$env:DATABASE_URL = "postgresql+asyncpg://payflow_test:payflow_test_password@127.0.0.1:5434/payflow_test"
alembic upgrade head

$env:PSP_DATABASE_URL = "postgresql+asyncpg://payflow_psp_test:payflow_psp_test_password@127.0.0.1:5436/payflow_psp_test"
alembic -c psp/alembic.ini upgrade head

python -m pytest app/tests -q
```

После работы закройте этот терминал, чтобы тестовые переменные окружения не использовались при обычном запуске приложения.

**macOS / Linux:**

```bash
DATABASE_URL='postgresql+asyncpg://payflow_test:payflow_test_password@127.0.0.1:5434/payflow_test' alembic upgrade head

PSP_DATABASE_URL='postgresql+asyncpg://payflow_psp_test:payflow_psp_test_password@127.0.0.1:5436/payflow_psp_test' alembic -c psp/alembic.ini upgrade head

DATABASE_URL='postgresql+asyncpg://payflow_test:payflow_test_password@127.0.0.1:5434/payflow_test' PSP_DATABASE_URL='postgresql+asyncpg://payflow_psp_test:payflow_psp_test_password@127.0.0.1:5436/payflow_psp_test' python -m pytest app/tests -q
```

Тесты Mock PSP запускаются отдельно с указанием каталога его тестов. Сетевое взаимодействие с провайдером в сервисных тестах подменяется тестовым клиентом.

## Проверки перед коммитом

В активированном локальном Python-окружении:

```bash
python -m pip install pre-commit ruff mypy
pre-commit install
pre-commit run --all-files
```

Локальные hooks используют Ruff и mypy из окружения. Если Ruff изменил файлы, проверьте изменения, добавьте их в индекс и повторите коммит.

## Полезные команды

```bash
# Состояние контейнеров
docker compose ps

# Логи приложений
docker compose logs -f app psp

# Пересборка после изменения Python-кода
docker compose up -d --build app psp

# Остановка без удаления контейнеров
docker compose stop

# Удаление контейнеров и сети с сохранением именованных томов БД
docker compose down
```

Основные базы хранятся в томах `postgres_data` и `psp_postgres_data`. Команда `docker compose down -v` удаляет тома и данные — не используйте её для обычного перезапуска.

Git переносит код и миграции, но не содержимое локальных баз и не `.env`. При работе с другого компьютера настройте его окружение и примените миграции отдельно.
